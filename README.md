# KeenSwitch

Chrome-расширение (Manifest V3), которое в один клик из попапа переключает текущее
устройство между политиками доступа (Policy) на роутере Keenetic — без захода в
веб-интерфейс роутера.

Аналог CLI-команды:

```
ip hotspot host <MAC> policy PolicyN
```

## Что требуется

* Роутер Keenetic с настроенными политиками доступа (KeeneticOS 3.x–5.x).
* Компьютер в одной сети с роутером — расширение ходит напрямую на его веб-интерфейс.
* Node.js 20+ и npm для сборки.
* Учётная запись роутера с правом менять настройки.

## Сборка и установка

```bash
npm install
npm run build
```

Сборка кладёт готовое расширение в `dist/`. Дальше:

1. Откройте `chrome://extensions`.
2. Включите **Режим разработчика**.
3. **Загрузить распакованное расширение** → выберите папку `dist`.

## Первоначальная настройка

Откройте настройки расширения (иконка → «Настройки»):

1. **Адрес веб-интерфейса** — тот же, по которому вы открываете панель Keenetic,
   например `http://192.168.1.1`. Схему можно не писать, подставится `http://`.
2. **Логин** и **пароль** от роутера.
3. Нажмите **Проверить подключение**. Chrome спросит разрешение на доступ к этому
   адресу — его нужно выдать: без него расширение не сможет ни ходить на роутер, ни
   отдавать ему сессионную cookie. После проверки заполнится список устройств.
4. **Моё устройство**: по умолчанию включено автоопределение — роутер сам сообщает
   MAC того, кто пришёл (RCI `whoami`), поэтому ничего выбирать не нужно. Если
   автоопределение даёт не тот MAC (VPN, мост, докстанция), переключитесь на ручной
   выбор из списка.
5. **Сохранить**.

Дальше работа — это клик по иконке и клик по нужной политике. Текущая политика
отмечена галочкой. «Без политики» снимает привязку: устройство начинает ходить по
политике по умолчанию.

## Проверка без расширения

Если что-то не работает, тот же цикл можно прогнать из терминала — скрипт
независим от расширения и печатает, что именно отвечает роутер:

```bash
node scripts/probe-router.mjs --url http://192.168.1.1 --login admin
```

Пароль спрашивается интерактивно (в историю команд не попадает). Скрипт покажет
модель роутера, список политик, политику по умолчанию, MAC текущего устройства и
его текущую политику. Переключить политику из терминала:

```bash
node scripts/probe-router.mjs --url http://192.168.1.1 --set Policy0
```

`--set none` снимает политику.

## Как это устроено

Схема RCI снята с живого роутера (KeeneticOS 5.01) и из кода веб-панели, а не из
документации — у Keenetic она между прошивками меняется.

**Авторизация** (`x-ndw2-interactive`):

```
GET  /auth  -> 401, заголовки X-NDM-Realm и X-NDM-Challenge, Set-Cookie
POST /auth  {"login": "...", "password": SHA256(challenge + MD5("login:realm:password"))}
GET  /auth  -> 200, если сессия жива
```

Имя сессионной cookie у каждой сессии своё (например `YN6zYK2JB8xV4E`), поэтому
расширение не разбирает cookie руками, а полагается на cookie jar браузера:
`credentials: 'include'` плюс host permission ровно на адрес роутера.

**Защита от CSRF.** KeeneticOS отвечает `403 Forbidden` на любой запрос к
`/rci/`, чей `Origin` или `Referer` не совпадает с самим роутером. Chrome же
обязательно проставляет к запросам расширения `Origin: chrome-extension://<id>`,
а убрать его из JS нельзя — fetch считает `Origin` и `Referer` forbidden
headers. Поэтому:

* `Origin` подменяется правилом `declarativeNetRequest` (session-scope,
  только адрес роутера, только запросы вне вкладок — трафик открытой веб-панели
  правило не трогает) — см. [`src/lib/dnr.ts`](src/lib/dnr.ts);
* `Referer` гасится через `referrerPolicy: 'no-referrer'` прямо в fetch.

На `/auth` эта проверка не распространяется — поэтому авторизация проходит даже
без подмены, а спотыкается уже первый запрос к `/rci/`.

**Команды**: `POST /rci/` c массивом объектов — путь команды разворачивается во
вложенный объект, ответ приходит массивом в том же порядке.

| Что нужно | Путь RCI |
| --- | --- |
| список политик | `show.sc.ip.policy` |
| политика по умолчанию | `show.sc.ip.hotspot.default-policy` |
| привязки политик к устройствам | `show.sc.ip.hotspot.host` |
| список устройств в сети | `show.ip.hotspot` |
| кто я для роутера | `whoami` |
| назначить политику | `ip.hotspot.host` |
| сохранить конфигурацию | `system.configuration.save` |

Назначение политики повторяет то, что шлёт сама веб-панель:

```jsonc
// назначить политику
{"ip": {"hotspot": {"host": {"mac": "…", "permit": true, "policy": "Policy0"}}}}
// снять политику
{"ip": {"hotspot": {"host": {"mac": "…", "permit": true, "conform": false, "policy": {"no": true}}}}}
```

После записи расширение перечитывает состояние с роутера и сравнивает его с
ожидаемым — «переключил» показывается только тогда, когда роутер это подтвердил.
Конфигурация сохраняется (`system.configuration.save`), иначе настройка потерялась
бы при перезагрузке роутера.

## Разрешения

* `storage` — хранение настроек.
* `declarativeNetRequestWithHostAccess` — подмена заголовка `Origin` (см. ниже).
  Работает только там, где выдано host permission, и не даёт расширению видеть
  остальной трафик.
* `optional_host_permissions: http://*/*, https://*/*` — **не выдаётся при
  установке**. Расширение запрашивает доступ в рантайме ровно к одному origin —
  тому, что вы ввели в настройках (`http://192.168.1.1/*`). В `chrome://extensions`
  видно, что фактически выдано.

Service worker используется потому, что попап закрывается по клику «мимо» и уносит
с собой незавершённые запросы, а смена политики с сохранением конфигурации занимает
пару секунд.

## Безопасность

Логин и пароль лежат в `chrome.storage.local` **в открытом виде** — Chrome не даёт
расширениям защищённого хранилища. Их прочитает любой, у кого есть доступ к вашему
профилю Chrome. Сам пароль по сети не передаётся: уходит только SHA-256 от
challenge и MD5-хеша, и только на указанный адрес роутера.

## Если расширение пишет «Роутер отклонил логин и пароль»

При верных логине и пароле причина почти всегда одна: сессия разъехалась.
KeeneticOS выдаёт **новую сессионную cookie и новый challenge на каждый
`GET /auth`**, а хеш пароля сверяется с challenge той сессии, cookie которой
пришла вместе с `POST /auth`. Любой посторонний `GET /auth`, вклинившийся между
ними, ломает авторизацию — и роутер отвечает `401`, неотличимым от настоящей
ошибки в пароле.

Расширение защищается от этого само: хендшейк single-flight (параллельные
запросы делят одну авторизацию) и повторяется один раз с новым challenge. Но
перебить сессию может и **открытая в соседней вкладке веб-панель роутера** —
она ходит на `/auth` сама. Если ошибка повторяется, закройте эту вкладку.

Проверить, что дело не в пароле, можно скриптом — он ведёт сессию вручную и от
браузера не зависит:

```bash
node scripts/probe-router.mjs --url http://192.168.1.1 --login admin
```

## Ограничения

* У роутера есть защита от флуда: если засыпать его запросами, он на несколько
  минут перестаёт принимать соединения на порт 80, продолжая отвечать на ping.
  Расширение роутер не опрашивает, но при отладке скриптами в это легко упереться —
  выглядит как «роутер недоступен».
* Работает только когда компьютер в одной сети с роутером. Иначе попап покажет
  «Роутер недоступен». (Если веб-интерфейс доступен снаружи по KeenDNS, можно
  указать этот адрес — но тогда host permission выдаётся на публичный домен.)
* В mesh-сети Keenetic политики живут на контроллере — указывайте адрес
  контроллера, а не экстендера.
* Автоопределение устройства опирается на то, что браузер ходит к роутеру напрямую.
  Через VPN или прокси роутер увидит чужой MAC — тогда выбирайте устройство вручную.
* macOS с включённым «Частный адрес Wi-Fi» показывает роутеру случайный MAC. Он
  стабилен для конкретной сети, так что всё работает, но в списке устройств
  компьютер может называться неузнаваемо.

## Скрипты

| Команда | Что делает |
| --- | --- |
| `npm run build` | типы + сборка в `dist/` |
| `npm run dev` | Vite в watch-режиме (HMR для попапа и настроек) |
| `npm test` | тесты разбора ответов роутера и MD5 |
| `npm run typecheck` | только проверка типов |

## Структура

```
manifest.config.ts        манифест MV3
src/lib/keenetic.ts       клиент RCI: авторизация, батч-запросы, разбор ответов
src/lib/md5.ts            MD5 (нужен для авторизации, в WebCrypto его нет)
src/lib/settings.ts       chrome.storage.local и host permission
src/lib/icons.ts          SVG-иконки интерфейса (Lucide-стиль)
src/ui.css                дизайн-система: токены тем, компоненты попапа и настроек
src/background.ts         service worker: вся работа с сетью
src/popup/                попап: список политик и переключение
src/options/              настройки: роутер, доступ, выбор устройства
scripts/probe-router.mjs  проверка роутера из терминала
tests/                    тесты
```
